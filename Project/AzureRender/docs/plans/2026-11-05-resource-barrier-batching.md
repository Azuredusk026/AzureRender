# 资源依赖批量提交

## 状态与目标

状态：CPU 契约及两配置检查通过，设备验证等待空闲 GPU。
目标是在同一提交位置批量记录缓冲资源依赖。
渲染图负责依赖顺序，记录器负责后端调用。
资源范围、访问条件及在途生命周期保持完整。

## 实测与来源

实际联合帧的主命令缓冲包含 4,934 次屏障调用。
该数量包含图像及缓冲屏障，具体组成仍需分解。
`RenderGraph::execute` 按资源逐条调用记录器。
同一过程入口的这些调用之间没有绘制或分发。

[Khronos 同步示例](https://docs.vulkan.org/guide/latest/synchronization_examples.html)说明保持同步语义的批量提交。
[Vulkan 同步规范](https://docs.vulkan.org/spec/latest/chapters/synchronization.html)定义阶段、访问范围及命令位置。
本单元据此评估提交组织，收益通过实际负载确认。
着色过程的成本继续独立测量。

## 模块与契约

`RenderGraph` 持有编译后的依赖描述和过程顺序。
`ICommandRecorder` 接收本次位置的缓冲屏障集合。
通用回退按集合顺序记录单条屏障。
`VulkanCommandRecorder` 将兼容集合转换为一次后端调用。

每条屏障保留句柄、偏移、大小和访问条件。
Vulkan 1.0 路径合并阶段掩码相同的连续屏障。
阶段掩码分别按单条路径的规则规范化。
同一缓冲句柄再次出现时开始新分组。
访问范围、阶段变化和原序列边界继续保留。
图像布局与过程内显式同步继续由其所属路径管理。

批量记录发生于过程入口和渲染过程之外。
调用方持有集合至记录结束。
后端资源保持存活至所属提交完成。
空集合记录为零次后端调用。

该能力服务蒙皮后读取、间接剔除及普通几何读取。
资源标识和具体角色、关卡数据保持所属模块边界。

## 实施顺序

1. 分解实际捕获中的屏障类型、范围及过程位置。
2. 补充多资源依赖、空集合、别名范围及顺序检查。
3. 实现公共回退、Vulkan 批量转换及渲染图接入。
4. 完成受影响的 CPU、双设备同步及资源释放检查。
5. 对照原生四帧和实际绘制、屏障调用数量。
6. 固定来源后按原帧数独立测量完整场景性能。

每个修改单元均先记录失败控制及通过条件。
定位十分钟，候选与短检二十分钟。
构建、采集和设备检查按原命令预算执行。
完整画质、CPU、GPU 及热状态门槛保持有效。

## 当前执行单元

基线为 `43681b6`，生产着色程序各五百三十五份。
假设为同位置、同阶段的独立缓冲屏障可共同记录。
公共回退保留逐条调用，Vulkan 路径记录兼容分组。
先用实际后端命令截获验证参数与分组。
CPU 夹具直接调用后端，持有虚拟句柄且不调用驱动。
该结果只证明命令转换，设备行为由后续 GPU 用例验证。

失败控制为新公共入口缺失及图接口分组检查失败。
受影响检查包括 RHI、渲染图及其契约检查。
每配置来源构建期限九百秒，短检查期限三百秒。
GPU 画面、同步与原生性能按用户安排延期。
当前变更作为待设备验证候选，完整验收保持原状态。

两配置结果及延期范围见[批量提交验证](../acceptance/nr/buffer-barrier-batching.md)。
