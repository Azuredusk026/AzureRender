# 关卡刷新数据释放

## 问题与交付

源码基线为 `48b04c7`。
[实际调用栈](../acceptance/nr/current-cpu-hotspots.md)包含关卡轮询中的 JSON 释放。
阶段观察记录轮询的局部高耗时帧。
本单元验证未变化刷新结果的主线程释放范围。

所属模块为 Runtime 的 `LevelSession`。
后台工作产生候选关卡及资产数据库。
主线程在未变化结果中发布资产数据库并保留当前运行场景。
候选文档及退休数据库由会话持有，交给下一后台工作释放。

会话最多保留一个待释放的刷新结果。
后台工作开始时显式清空退休数据，再继续刷新及加载。
取消、版本拒绝、场景提交及当前资产可见性保持所属规则。
会话关闭继续等待已启动工作，并释放全部拥有的数据。

## 验证与预算

实际会话使用含大文档的最小关卡复现释放位置。
逐次轮询单独统计大块内存的主线程释放。
未变化刷新保持场景版本及运行时实体稳定。
重复刷新及关闭分别核对保留量和资源释放。

先记录主线程释放的实际失败，再实施所有权转移。
两个配置覆盖会话、预加载、取消、组件和游戏流程回归。
原生四帧保持原冻结参考的严格字节门槛。
生产程序、项目输入及原性能条件保持原验收规则。

定位十分钟，候选及短检二十分钟，探索三十分钟。
两配置宿主及受影响目标构建分别九百秒。
原生四帧九百秒，短时原生命令三百秒。
本单元只验证未变化刷新，其他释放路径按独立证据调度。

## 执行结果

实际失败控制三轮主线程大块释放累计为 7,681,302 字节。
两配置的三轮候选结果均为零，持有量逐轮稳定。
场景版本及实体数保持一致，会话关闭释放检查通过。
范围及单位见[验证记录](../acceptance/nr/level-refresh-retirement.md)。

两配置各二十八项 CPU 检查及原生四帧冻结对照通过。
GPU 机制按相同可执行文件及所用程序引用既有检查。
短时 CPU 工作 P95 为 19.80 毫秒，GPU 为 35.13 毫秒。
运行中热状态失败，完整帧预算及用户画质保持未通过。
