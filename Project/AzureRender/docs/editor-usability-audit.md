## 固定场景根的含义

建议使用固定的场景容器行。
它显示场景名，所有顶层物体列在其下。
容器接受拖放，负责表达对象属于哪个场景。
对象数据仍以空父标识表达顶层关系。

Unity 的场景容器与普通 GameObject 有不同职责。
实际父物体会引入变换继承、删除和脚本语义。
采用实际父物体时，需要相应设计保存与迁移规则。
用户已确认采用场景容器行，场景实体结构保持其语义。

## 架构方案

| 方案 | 范围 | 成本与限制 |
| --- | --- | --- |
| A：局部控件整理 | 命名、重复按钮和提示 | 成本低，跨面板操作仍需逐项协调 |
| B：围绕操作流程整理 | 命令、选择、层级、设置和工作区 | 成本中等，可分阶段交付 |
| C：整体重建编辑器外壳 | 面板生命周期和全部布局重构 | 成本高，既有功能回归范围大 |

推荐方案 B。
用户的问题涉及多个面板间的职责和操作一致性。
各方案均沿用 ImGui、GLFW 和 Vulkan。
维护内容是本地编辑器代码、布局与兼容配置。
交互功能本身适用于本地离线使用。

## 执行顺序

以下为执行计划。UX-A、UX-B 已完成，UX-C 开发中。

UX-A 修改层级面板、编辑操作和层级服务。
补充同级移动、解除父级和撤销测试。
通过后提交 `feat(ux-a)`。

UX-B 修改工作区装配、主工具栏和视口布局。
验证布局恢复、尺寸预算和输入回归。
通过后提交 `feat(ux-b)`。

UX-C 使用脚本服务提供从选中对象附加脚本的入口。
验证合法资产、错误类型、撤销和保存重开。
通过后提交 `feat(ux-c)`。

UX-D 分离普通设置与代码扩展配置的呈现职责。
保留项目配置兼容并检查示例交付路径。
通过后提交 `feat(ux-d)`。

UX-E 执行完整非 GPU 回归及受影响界面检查。
记录真实结果与环境待项，通过后提交 `feat(ux-e)`。

| 代号 | 交付内容 | 主要范围 |
| --- | --- | --- |
| UX-A | 创建与层级操作闭环 | 明确命名、场景容器、拖放、多选、撤销和保存 |
| UX-B | Unity 风格工作区 | 层级、属性、资源区、主工具栏和视口工具布局 |
| UX-C | 组件与脚本工作流 | 附加组件、附加脚本、编辑属性和失败反馈 |
| UX-D | 设置与扩展归属 | 个人偏好、项目设置、专用技术入口和示例内容 |
| UX-E | 集中工作流复核 | 创建、编辑、运行、保存重开和发布 |

UX-B 继续检查视口焦点、导航和工具切换。
UX-C 先核对脚本创建、编译和附加的真实链路。
UX-D 检查模板、配置、运行与发布的依赖范围。
这些范围尚未全部排查，不能标记已实现。

每项修改执行所属构建和受影响短检查。
层级修改覆盖变换保持、循环引用和撤销重做。
扩展归属修改覆盖示例加载与通用项目发布。
完整工作流与人工体验复核集中在 UX-E。

面板负责呈现、选择和交互反馈。

检查依赖和实际调用方向，确认职责边界有效。
